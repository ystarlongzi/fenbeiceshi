# 服务器部署

更新：2026-10-24。适用于 `fenbeiceshi.com` 的静态站点。脚本和工作流已在仓库中实现；GitHub Secrets、服务器工具、证书、DNS、Cloudflare 设置及公网可达性由首次部署时配置和验收。本文所有 `<...>` 都需要替换成实际值，禁止原样执行。

## 1. 运行前提与目录

构建机使用 Node `>=24.11.0 <27`、npm、Git、tar 与 OpenSSH；Actions 固定使用 Node 24。源站为 Linux，具备 Bash、GNU tar/coreutils/findutils、gzip、curl、flock、Nginx 与 OpenSSL。自动准备支持 Linux/systemd；缺失软件仅在 Ubuntu/Debian 通过 apt-get 安装。已有其他 Linux 环境应先由管理员补齐工具与服务。

本站默认目录：

```text
/www/wwwroot/fenbeiceshi/
├─ releases/<版本号>/          完整静态输出、版本标记与成功发布标记
├─ current -> releases/...     当前已启用版本
├─ shared/_next/static/        新旧版本共用的哈希资源
├─ .incoming/                 上传临时包，退出时清理
└─ .deploy.lock               初始化、发布与回滚共用的锁
```

其他服务器路径：站点配置 `/etc/nginx/conf.d/fenbeiceshi.conf`，证书 `/etc/nginx/ssl/fenbeiceshi.com/`，DNS 凭据 `/etc/fenbeiceshi/cloudflare.env`，独立 ACME 目录 `/root/.acme.sh-fenbeiceshi`，日志 `/var/log/nginx/fenbeiceshi.{access,error}.log`。

部署目录必须是至少三级、以 `/fenbeiceshi` 结尾的绝对路径，域名只能为 `fenbeiceshi.com`。脚本同时在本机和服务器校验，拒绝路径穿越、链接和其他域名。更改目录前先确认未占用，保证发布用户能写本站目录，Nginx worker 能读取目录及文件。

## 2. 首次配置 GitHub

在仓库 Settings → Environments 创建 `production`，允许 main 分支部署。所需 Secrets 可配置在该环境；没有环境级覆盖时也可使用仓库 Secrets。

| Secret            | 值与用途                                                                            |
| ----------------- | ----------------------------------------------------------------------------------- |
| `SSH_HOST`        | 服务器 IPv4 地址或主机名，不含协议与端口                                            |
| `SSH_USER`        | SSH 用户；勾选初始化时必须为 root                                                   |
| `SSH_PORT`        | 实际 SSH 端口，省略默认 22                                                          |
| `SSH_PRIVATE_KEY` | 专用私钥全文，保留 BEGIN/END 与换行                                                 |
| `SSH_KNOWN_HOSTS` | 经受信通道核验指纹的 known_hosts 行，Actions 必填；非 22 端口通常使用 `[主机]:端口` |
| `CF_TOKEN`        | 仅限本站 zone 的 Cloudflare API Token，初始化时使用                                 |
| `CF_ZONE_ID`      | `fenbeiceshi.com` 的 32 位小写十六进制 Zone ID，初始化时使用                        |

Token 仅授予本站 zone 的 Zone:Read 和 DNS:Edit。私钥对应的公钥须已安装在目标账户的 authorized_keys；不要把私钥、Token 或服务器配置值提交到仓库。主机指纹须通过服务器控制台等受信通道核验，单独取得 ssh-keyscan 输出不构成核验。

配置以下 Variables；省略时使用表内默认值：

| Variable          | 默认值 / 要求                                                      |
| ----------------- | ------------------------------------------------------------------ |
| `DEPLOY_PATH`     | `/www/wwwroot/fenbeiceshi`                                         |
| `NGINX_CONF_PATH` | `/etc/nginx/conf.d`；必须被现有 Nginx 主配置 include `目录/*.conf` |
| `CERT_ROOT`       | `/etc/nginx/ssl`                                                   |
| `DNS_ENV_FILE`    | `/etc/fenbeiceshi/cloudflare.env`                                  |
| `ACME_HOME`       | `/root/.acme.sh-fenbeiceshi`                                       |
| `SSL_EMAIL`       | 无默认值；首次初始化须填真实联系邮箱                               |

首次上线先填齐配置，再手动运行发布。日常发布可换成仅有本站目录权限的专用用户；初始化仍需 root，并使用对应私钥。当前应用不需要 `ENV_PRODUCTION` 等应用 Secrets，部署变量不会注入浏览器代码。

## 3. 域名、TLS 与首次上线

1. 在 Cloudflare 将主域名解析到源站，配置 www 入口；服务器允许所需的 80/443 入站流量，SSH 端口按实际配置开放。使用 DNS-01 申请证书还需要源站能通过 HTTPS 访问 GitHub、Cloudflare API 与 Let's Encrypt。
2. 确认 `NGINX_CONF_PATH` 已被主配置加载，且 `nginx -t` 通过；初始化不改写 Nginx 主配置。对于自定义目录，将 Variable 指向其真实 include 目录。
3. 打开 Actions →「构建并部署分贝测试」→ Run workflow，选择 main，勾选「初始化或检查部署环境」。
4. 工作流先完成代码检查与集成演练，再打包、准备 SSH，随后初始化并发布。初始化会校验 Cloudflare zone，补齐工具，在独立 ACME 目录安装固定版本 acme.sh，通过 DNS-01 申请主域名与通配符证书，登记安装路径、自动续期和 reload 命令，并安装本站 Nginx 配置。
5. 源站 443 与匹配域名的有效证书就绪后，Cloudflare 使用 Full (strict)。可先通过下一节的本机初始化命令完成源站准备，再运行不勾初始化的发布；首次发布的公网检查未通过时，先修复 TLS/DNS/代理配置，再重跑工作流。
6. 源站和公网健康检查全部通过才提交新版本。首次发布失败会移除失败的 current；已有成功版本时会恢复旧版。证书与站点配置初始化出错会尝试恢复原文件，恢复失败会保留受限备份并明确报告路径。

HTTP 和 www 都永久跳转到 `https://fenbeiceshi.com`，保留请求路径与查询。HTML 使用 `no-cache`，哈希资源使用一年 immutable，`/_release.txt` 使用 `no-store`。Cloudflare 自定义缓存规则应让 HTML 可及时更新，并排除版本标记；脚本不修改 Cloudflare 的 TLS/缓存/WAF 设置，也不会自动清除其他缓存。

Nginx 的主文档和静态资源响应头允许 `microphone=(self)`。Cloudflare 的响应头规则也必须保留该策略。来源政策不会替代用户授权，实际手机/桌面麦克风仍需实测。[Cloudflare Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)、[麦克风权限](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)。

## 4. 本机初始化与发布

仅在本机需要直接部署时创建本地配置：

```sh
cp deploy/.env.example deploy/.env.local
cp deploy/cloudflare.env.example deploy/cloudflare.local
chmod 600 deploy/.env.local deploy/cloudflare.local
```

部署模板已预填本站服务器地址、SSH 端口与联系邮箱；复制后核对密钥路径和服务器目录，并在 `deploy/cloudflare.local` 填写实际 DNS Token 与 Zone ID。`SSH_PRIVATE_KEY_FILE` 与 `SSH_KNOWN_HOSTS_FILE` 是本机文件路径，支持 `~/`；其余初始化路径为服务器路径。配置仅作为数据解析，不展开 `$HOME` 或执行命令。私钥不要写入文件正文。

默认读取 `deploy/.env.local`，也可用 `--env-file <路径>`。优先级为命令参数 → 环境变量 → 配置文件 → 默认值。Actions 仅使用其 Secrets/Variables，不自动读取本机副本。

```sh
npm run deploy:setup -- --bootstrap --dry-run
npm run deploy:setup -- --bootstrap
```

`--dry-run` 只校验参数与凭据格式、显示非秘密配置，不连接服务器，也不能验证 SSH、证书或远端服务。`--bootstrap` 从本机受限凭据文件读取 Token；Actions 从 Secrets 读取。省略 `--bootstrap` 时要求服务器工具、ACME 和 DNS 凭据已就绪：

```sh
npm run deploy:setup -- --dry-run
npm run deploy:setup
```

日常本机发布先执行完整检查，再以唯一版本号打包。以下为示例，版本号应随每次发布更换：

```sh
npm ci
npm run check
npm run deploy:pack -- --release release-20261024-01
npm run deploy:static -- --artifact artifacts/fenbeiceshi-release-20261024-01.tar.gz --release release-20261024-01 --dry-run
npm run deploy:static -- --artifact artifacts/fenbeiceshi-release-20261024-01.tar.gz --release release-20261024-01
```

打包会保留原始 out，在临时目录加入 `_release.txt`、首页 JS/CSS 资源清单和含 revision/builtAt 的 `release.json`，生成 tar.gz 及同名 `.sha256`。可通过 `--revision <40位提交SHA>` 指定提交，否则读取当前 Git HEAD。正式发布优先使用 Actions，以明确提交与构建的一致性。重复版本号会被拒绝；包与 SHA-256 文件必须保持同目录。

## 5. 自动发布、验收与回滚

main 推送自动运行生产发布；普通 Pull Request 与非 main 分支只检查。Actions 版本号为 `提交SHA-运行编号-重试次数`。每次工作流在同一个 runner/job 内完成构建、打包和 SSH 传输，不上传 GitHub Artifacts。

远端先获取文件锁，校验上传包 SHA-256、tar 路径与文件类型，拒绝隐藏文件、软链接及路径穿越，检查三语关键页面、录音资源与许可证，再归并哈希资源并原子切换 current。健康检查同时访问本机源站与公网，验证版本标记、三语首页/指南/分贝指南/记录页、录音脚本、robots、sitemap、首页资源 MIME、麦克风权限策略和真实 404。

发布日志中应记录成功版本号。首次上线和每次影响音频/浏览器行为的更新，另外实测：三语页面、主题与语言、真实麦克风授权/拒绝/停止释放、录音、保存报告、MP3/PCM 下载及手机设备。自动 HTTP 检查不能代替浏览器音频与设备验收。

发布后至少观察 10 分钟本站错误日志、5xx、关键页面加载及功能；异常时先停止后续发布，保留错误上下文并回滚。可在服务器只读查看保留版本与当前指向：

```sh
readlink -f /www/wwwroot/fenbeiceshi/current
ls -lt /www/wwwroot/fenbeiceshi/releases
```

需要回退时，打开 Actions →「回滚分贝测试」，选择 main 并输入仍保留的成功版本号；无需重建或再次上传。也可在本机执行：

```sh
npm run deploy:rollback -- <已保留版本号> --dry-run
npm run deploy:rollback -- <已保留版本号>
```

回滚后仍执行相同健康检查；失败会尝试恢复回滚前的版本。服务器只保留当前加最多两个成功旧版本；已清理或从未成功发布的版本不可回滚。老哈希资源保留七天缓冲，并保留所有可回滚版本仍引用的资源。

网页回滚不回写浏览器存储。当前摘要封装为版本 3，旧应用可能拒绝读取；涉及跨存储版本回退前先导出重要报告，不能通过删字段或清空存储伪造兼容。

## 6. Linux 集成测试

`npm run check` 包含跨平台部署测试；其中三个真实 Linux 用例默认跳过，由独立的集成入口执行。入口要求 Linux/root，且本站两个域名都只能解析到 `127.0.0.1`，会占用测试环境的 80/443。不要在生产服务器执行。

本机可使用仓库提供的容器定义：

```sh
docker build -f deploy/tests/Dockerfile -t fenbeiceshi-deploy-test:local deploy/tests
docker run --rm --network none   --add-host fenbeiceshi.com:127.0.0.1   --add-host www.fenbeiceshi.com:127.0.0.1   --mount "type=bind,source=$PWD,target=/workspace,readonly"   --workdir /workspace fenbeiceshi-deploy-test:local
```

构建测试镜像需要网络；执行演练时禁用外部网络，源码只读挂载，所有版本、证书和 Nginx 进程都留在临时容器。验证真实 TLS、三版保留、哈希资源缓冲、坏版本恢复、手动回滚、Nginx 跳转/缓存/麦克风头/404，以及初始化配置和证书失败恢复。Cloudflare API、实际 ACME 签发、系统软件安装及 cron 在测试中隔离或替身处理，不会操作线上服务。

CI 在部署脚本、工作流、检查脚本、包清单、锁文件及相关配置变更、首次推送和手动运行时执行 Linux 演练。生产发布工作流在演练前备份 runner 的 hosts，结束后恢复；恢复失败阻止发布。对比提交失败时也会停止，不把失败当作无变更。

## 7. 故障处理与维护

| 现象                              | 检查与处理                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------------- |
| 缺少 Secret 或主机公钥变化        | 核对 production 环境、SSH 用户/端口及经核验的主机指纹；不跳过主机核验              |
| Nginx 未加载目录                  | 用管理员权限检查 `nginx -T` 的 include，设置正确 NGINX_CONF_PATH；初始化不改主配置 |
| DNS-01 / Cloudflare zone 校验失败 | 核对本站 Token 的 zone 范围、Zone ID 与源站出口网络；不打印 Token                  |
| Full (strict) 失败                | 检查源站 443、有效期、SAN、证书链和私钥匹配，再检查 Cloudflare 模式                |
| 源站正确而公网版本不符            | 检查 DNS、代理、HTML/标记缓存及 Worker；发布已尝试恢复旧版                         |
| 页面正常但麦克风不可用            | 检查 HTTPS、Permissions-Policy、Cloudflare 响应头与浏览器/系统授权                 |
| 锁超时                            | 确认是否仍有初始化/发布/回滚运行，等待或诊断持锁进程，不删除活动锁绕过保护         |
| 初始化恢复失败                    | 按日志定位保留的受限备份，修复配置与证书后先执行 `nginx -t` 再 reload              |

自动续期使用独立 ACME_HOME 的 cron，不覆盖其他已有任务；更换 DNS Token 后重新运行初始化以同步受限文件与续期配置。更换 Nginx 模板或证书路径也需重跑初始化，普通内容发布不 reload Nginx。定期检查证书期限、续期日志、本站磁盘占用和服务器回滚版本。
