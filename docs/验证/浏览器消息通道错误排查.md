# 浏览器消息通道错误排查

日期：2026-10-21。本轮承接帮助内容验证中记录的 Chrome 控制台消息通道错误。

## 结论

已确认这条错误来自 Chrome 的扩展环境，不依赖本站的应用代码；没有修改业务代码，也没有添加全局异常过滤。

此前“来源未确认”的状态由本次隔离结果更新。尚未逐个定位具体扩展名称；扩展管理页访问被浏览器 URL 安全策略阻止，因此没有继续读取管理页、停用或卸载扩展。

最小页面没有脚本、样式或音频逻辑。Chrome 在其上仍注入了扩展内容，独立于应用即可触发错误，这排除了本次错误由 FAQ、React 生命周期或录音消息处理产生的可能。

Chrome DOM 可见 AIX 工具面板及一个扩展脚本地址；另一个扩展地址出现在独立的 DOM 异常堆栈中。消息通道错误本身没有指出扩展 ID，不能仅凭同页出现就断言一定是其中某个扩展。相关地址只作为本次观察证据，未读取完整扩展清单或浏览器配置。

## 错误机制与代码核对

完整报错对应 Chromium 扩展消息模块的 `kClosedWhileResponsePendingError`，定义在 [ExtensionMessagePort 源码第 54–56 行](https://github.com/chromium/chromium/blob/main/extensions/browser/api/messaging/extension_message_port.cc#L54)。它描述扩展监听器承诺异步响应，但通道在响应前关闭的情况。[Chrome 消息传递文档](https://developer.chrome.com/docs/extensions/develop/concepts/messaging)说明了 `runtime.sendMessage`、`runtime.onMessage`、`return true` 与 `sendResponse` 的关系。

本轮检索 `src/`、`public/` 与最终 `.next/static/chunks/`，没有发现 `chrome.runtime`、`browser.runtime`、`runtime.sendMessage`、`runtime.onMessage` 调用或该错误文本。产物中存在标准 `MessageChannel` 和 `message` 监听，不能仅因名称相似就等同于 Chrome 扩展消息协议。

本站自己的消息路径是 `src/features/audio-recording/mp3-export.ts`、`mp3.worker.ts` 的 Web Worker，以及 `recorder.ts` 与 `public/audio/pcm-recorder.js` 的 AudioWorklet 端口；它们使用标准 `postMessage` / `onmessage`，不使用扩展的异步应答协议。此次纯静态隔离页不包含这些路径，依然复现原错误。
